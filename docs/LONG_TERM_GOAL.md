# 长期目标、最小验证与工作安排

计划日期：2026-10-19（Asia/Shanghai）。这是项目路线，不是已完成的游戏能力，也不是自动启动的定时挂机任务。

## 1. 长期目标怎样定义

目标草案：**在用户确定的月度现金预算、每日人工时间和游戏运行时间内，优先使用官方已有减负功能，用小型本地自动化补齐重复操作，让一个指定角色达到用户认可的实用成品标准，并持续保持。**

“所有玩法”作为覆盖清单逐项管理。每项可以采用官方自动、自编流程、辅助提示或人工参与；目标版本、等级、组队条件和活动时间明确后，才讨论该项是否能完整自动执行。不能把“能识别图片”或“六项日常跑完”当成全玩法完成。

账号成品与工具能力分开验收：

| 目标线 | 必须明确的标准 | 完成依据 |
|---|---|---|
| 账号成品 | 等级/停级点、门派、用途、门派技能与修炼、装备、宠物、指定内容 | 本机账号快照、实际属性及用户指定内容的实战结果 |
| 工具能力 | 覆盖的玩法与分支、运行条件、可接受的人工介入和资源上限 | 各玩法的真实完成证据、失败记录、成本和稳定性数据 |

用户已确认新增现金预算为 **0 元**；成品定义和人工分钟上限仍待选择。临时按“日常和常规副本实用号、优先降低现金投入”的草案安排，不据此承诺具体养成时间或装备水平。用户改变目标时，先修订标准再扩大开发。

配置结构见 [ACCOUNT_GOAL.example.json](ACCOUNT_GOAL.example.json)。示例中的 null 表示待确认，不能解释为无限预算、无限人工时间或已满足条件。真实账号资料仅放被忽略的本机配置。

## 3. 控制总成本的方法

成本需要分开记，不能把银币等游戏货币直接混算为人民币：

1. 现金：托管/设备、模型 API、游戏充值或官方付费减负等实际账单。
2. 游戏资源：现金、信誉、银币、金币、药品等在本轮前后的净变化。
3. 人工：每天登录/验证、补物资、处理异常的实际分钟。
4. 开发维护：每个玩法的开发、改版修复和异常分析时间。

先比较玩法对成品目标的推进、收益和消耗，再决定当天执行顺序。无需为“覆盖率”执行没有收益或维护成本过高的玩法。开发使用现有已获准环境；生产流程不启用新增计费模型 API。普通识别、等待、已知按钮和重复流程使用本地规则/OCR。未知情况停止并进入人工或离线分析，不逐帧调用模型。

运行采用单账号、限定每日窗口、每项次数和消耗上限；达到目标、次数或时间上限就退出。稳定流程可持久化进度，下一次启动仍以游戏内当前状态重新确认。处理不了的新画面停止并收集脱敏证据。

新增现金支出上限已确认为 **0 元**：不购买服务器/硬件、不充值、不新购付费减负、不启用新增计费模型 API，也不默认使用带自动续费的试用。优先利用已有且获准使用的资源。已有设备、订阅额度、开发和人工时间仍分别记录，不能称为零资源消耗或无限免费。

用户此前希望游戏不占用本人设备；0 元预算不视为撤销该要求。现有电脑可用于已授权的离线开发，但不默认转为本机长期挂机。目前没有免费、获准且通过游戏验证的远程运行环境，因此 V0/V1 的真实游戏验收仍缺前置条件。外部环境条件未满足时继续做离线准备，不报真实游戏通过。

## 5. 两次最小验证

### V0：最快验证游戏任务闭环

准备：一个客户端正常接受的 Windows 环境、更新完毕的官方客户端、用户亲自登录并选定角色、当前可做的物资修业及足量物品。第一轮没有自动采购、战斗或跨玩法调度。

流程：

```text
实时截图 → microvision → 当前物资任务与计数N
  → 背包物品/数量确认 → 内置任务追踪或已校准的返回操作
  → 指定NPC与交付物再次核对 → 提交一次
  → 明确完成反馈 + 游戏计数N→N+1 → 停止
```

通过条件：

- 当前角色、任务原文、物品、数量、初始计数有记录；不是沿用历史任务示例。
- 用户已做的登录/选角记为用户操作，程序执行的动作单独记录。
- 正确目标上的实际交付有提交前后证据；完成反馈和计数变化一致。本版计数不可读就记为未通过。
- 缺物、未支持分支、识别歧义、失焦、错窗、断线或超时停止，没有误交、误点或假成功。
- 仅完成一次，不接下一环；没有额外采购、充值或未计划资源消耗。

若当前随机任务不是支持的物资分支，记录未支持并停止；人工准备另一条可验证样本也必须写清。游戏内消耗并不因无需充值而变成零成本。

V0 只证明某个条件下的一次修业闭环，不证明自动登录/选角、全天稳定或其他任务可用。

### V1：补齐此前要求的完整入口流程

在 V0 的基础上，实现识别登录页→等待用户在客户端输入凭据并处理安全验证→识别目标区服和人物→确认选中→进入游戏核对身份→完成一次支持的修业。

账号密码和验证码不进入聊天、配置、日志或模板。V1 仍是人工凭据输入的登录接续，不宣称无人值守重登。V1 的角色与任务证据独立保存，不能用 V0 结果代替。

## 6. 接下来实际开发的工作包

原细化任务表仍以 [TASKS.csv](../TASKS.csv) 为准。为了尽早验证任务闭环，V0 可在用户已登录选角后先做 T07–T11；T05/T06 随 V1 补齐，整体完成标准不变。

| 工作包 | 主要职责 | 依赖和验收 |
|---|---|---|
| A 环境与校准 | 确认可运行环境；采集只含必要区域的当前游戏真图；核对官方减负 | 环境不过关，停止扩展开发投入；先手动证明该任务可做 |
| B 桌面基础 | 唯一窗口、实时截图、坐标、单次点击/按键、用户停止、帧时间和画面摘要 | 先接停止与记录，再验收输入；错窗/失焦/尺寸变化拒绝 |
| C 识别与物资流程 | 复用 microvision；读任务、计数、背包、NPC和交付，新增必要模板 | 可与 B 并行做离线识别；实际输入待 B 完成 |
| D 独立验收 | 复核角色、动作归属、游戏完成证据、资源消耗、异常停止 | B/C 合并后做 V0；实现方不能只依据自己打印的 success 判通过 |
| E 登录选角 | 登录等待、区服/人物唯一匹配、选中态、入场身份确认 | V0 后接 V1，也可并行做离线页面识别 |

这些是后续实施分工，本轮只完成计划编制和复核，没有开始 A–E 实际开发或购买环境。当前按已确认的 0 元预算推进；A 的环境条件未满足时，B/C 仅做离线开发和模拟回放。成品标准仍需用户确定。

## 7. 从一次成功走向长期使用

| 阶段 | 产物 | 下一阶段门槛 |
|---|---|---|
| M0 目标与资源盘点 | 成品标准、预算、人工分钟上限、官方功能清单 | 用户认可标准、环境路线和可接受投入 |
| M1 运行环境 | 正常登录/入场/截图/单次输入的证据 | 目标为远程运行时，额外验证远程查看关闭/会话状态变化后的行为 |
| M2 V0任务闭环 | 一次物资修业的真实完成证据 | 无假成功、误交和错误角色操作；未支持条件可停止 |
| M3 V1完整入口 | 人工凭据登录接续、自动选人和一次修业 | 各步均有动作后新画面与最终完成证据 |
| M4 有限重复与分支 | 不同真实样本、失败分类、人工干预和成本记录 | 与用户约定试用门槛；小样本结果只报告实测，不推断长期保证 |
| M5 六项日常 | 每项独立流程及官方功能复用，随后组合调度 | 每项及组合切换分别验收，资源/组队/次数上限都生效 |
| M6 养成调度 | 成品目标差距表、每日优先级、周报、消耗限制 | 以实际属性/资源改善和指定内容表现验收 |
| M7 其他玩法覆盖 | 逐项列出副本/周常/活动/社交/PVP的覆盖方式 | 按收益和维护成本推进；每项新增流程另有验证，不能提前承诺全自动 |

M4 可先约定“同分支最多 10 次受监督尝试”作为诊断批次：记录真实完成数/尝试数、人工干预、失败原因、耗时、资源消耗和假成功。10/10 只表示这批样本通过，不是 100% 长期可靠性。异常不靠无限重试掩盖；首个误交或假成功就暂停该流程并修复。

六项日常扩展优先复用修业原语到修炼、宝图等，再根据实际组队门槛、官方自动功能和收益决定巡游/降妖/除魔的次序。这个工程顺序不是固定的每日游戏顺序；每日执行顺序还要看现金、信誉、银币和目标差距。
